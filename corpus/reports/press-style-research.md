# 発表文・報道文の文体調査と lint の press プロファイル校正（2026-09）

`press-japanese` スキル（`skills/press-japanese/`）の設計根拠。生成AIが登場する前の新聞・大企業のプレスリリースの作法を規範資料から整理し、生成AI登場前のニュース文で `lint.py` の検出器を実測して `--genre press` の閾値を決めた。あわせて、この環境で取得できなかった資料（大企業のリリース本文）と、それを取得できる環境で再校正する手順を残す。

## 1. 目的と範囲

目的は三つ。(1) プレスリリース・報道記事・HP掲載のお知らせ・研究成果リリースが、生成AI以前から守ってきた構成と表記の作法を、出典つきで規範化する。(2) その文体に `natural-japanese/scripts/lint.py` を当てたときの誤検知を実測し、`press` プロファイルを校正する。(3) 「ソースにないことは書かない」を機械検査に落とすため、`factcheck.py` が照合すべき要素（数値・日付・固有名詞・引用・最上級）を決める。

参照する人間側の文章は「確実に生成AIではないもの」に限った。具体的には、2022年以前に公開された規範資料と、2005〜2016年が中心のニュース文（後述）。ウェブメディアの記事は使っていない。

## 3. 生成AI登場前のニュース文の実測

### 3.1 データ

tanreinama/Japanese-Fakenews-Dataset（GitHub）の `fakenews.csv`。ウィキニュース日本語版の記事（CC BY 2.5）と、GPT-2 日本語版 medium で生成した偽記事の混合コーパスで、`isfake=0` が人間の原文（3,685本）、`isfake=2` が全文生成（4,671本）。人間の原文で本文中に最初に現れる西暦は2005〜2010年が中心で、2017年以降は1本〜13本しかない。生成AIによる執筆・校正が混入している可能性はほぼ排除できる。

ウィキニュースはボランティアが新聞の作法に沿って書くニュースサイトであり、新聞そのものではない。特徴として「朝日新聞によると」型の帰属句がほぼ全文に付き、本文は段落分けのない1段落で収録されている。だから段落構造の検出器は評価できず、文単位・語単位の検出器だけを見る。大企業のプレスリリース本文は§5のとおり未計測。

サンプルは人間800本・GPT-2 400本（本文300字以上、seed 42）。再現は `corpus/experiments/press/analyze_wikinews.py`。

### 3.2 lint の検出器ごとの文書発火率（デフォルト閾値）

| 検出器 | 人間（n=800） | GPT-2（n=400） | 判断 |
|---|---:|---:|---|
| `low_burstiness` | **72.8%** | 53.3% | 弁別力が逆転。ニュース文は5W1Hを詰めた長めの文が均質に並ぶ文体。press では無効化 |
| `translationese_morph`（〜することができ） | 4.0% | 9.8% | 弁別力あり。ただし発表文では慣用なので severity を info に |
| `translationese` | 1.0% | 4.3% | 同上 |
| `low_sentence_variance` | 2.8% | 3.5% | 弱い。そのまま |
| `forbidden_phrase` | 0.8% | 2.3% | そのまま |
| `inanimate_subject_morph` | 0.4% | 1.5% | そのまま |
| `english_syntax_inanimate_subject` | 0.3% | 1.0% | そのまま |
| `repeated_sentence_lead` | 0.4% | 0.8% | 帰属句の反復で発火。そのまま（business 同様に閾値7） |
| `nominal_ending`（欠如） | 0% | 0.3% | 本文の体言止めは1割程度で、欠如を疑う根拠がない。press では無効化 |
| `low_lexical_diversity_ttr` | 0.1% | 0% | そのまま |

`--genre business` でも数値は同じ（違いは構造層の無効化のみで、この本文には構造がない）。

読解負荷レーン（`--reading-load`）は人間側で `sentence_too_long` 79.8%、`kanji_run` 41.3%、`buried_list` 23.9%、`no_chain` 11.0%、`double_negative` 1.5%。一文長の目安90字は人間のニュース文の大半に当たるため、press では100字に緩めた。それでも当たるので、このレーンは「指さし」として使う。

### 3.3 文体統計（人間のニュース文、n=800）

| 指標 | 中央値 | 10〜90パーセンタイル | GPT-2（中央値） |
|---|---:|---|---:|
| 一文の平均字数 | 61.5字 | 43.9〜87.8字 | 74.3字 |
| 一文の長さの変動係数 | 0.47 | 0.31〜0.66 | 0.48 |
| 文末が常体（だ・である・した等） | 88.9% | 66.7〜100% | 92.3% |
| 文末が敬体（です・ます） | 0% | 0〜0% | 0% |
| 体言止めの割合 | 8.3% | 0〜28.6% | 0% |
| 帰属表現（によると・としている・と発表した等）／文 | 0.50 | 0.07〜0.86 | 0.20 |
| リード（帰属句を除いた最初の文）の字数 | 79字 | 46〜133字 | 70字 |
| 「」の数／記事 | 2 | 0〜7 | 4 |
| 半角数字の数／記事 | 28 | 13〜55 | 31 |
| 全角数字の数／記事 | 0 | 0〜0 | 0 |
| 最上級・評価語（世界初・最大・画期的等）の数／記事 | 0 | 0〜1 | 0 |

割合で見る指標（n=800の平均）: リードに日付（「〇日、」）を含む 42.8%（GPT-2: 9.5%）、リードの述語が「発表した」「決定した」「〜した」型 66.4%（GPT-2: 18.0%）。

読み取れること。(1) ニュース文は常体で、敬体はゼロ。発表文（敬体）と記事（常体）の区別は文体の最も強い信号になる。(2) 数字は算用数字（半角）で、全角数字と単位つき漢数字はほぼ出ない。記者ハンドブックの方針と一致する。(3) 一文は60字前後で、変動係数0.47は均質とは言えないが、`low_burstiness` の閾値（モーラ近似）には多くが引っかかる。(4) リードは日付と「発表した」型の述語を持ち、2020年代初頭の生成モデルはこの型を再現できていなかった（日付43% vs 10%、述語66% vs 18%）。現行の大規模モデルがどうかは未計測だが、`news-article.md` の品質基準として「リードに日付」「述語は過去の動作」を明示する根拠にはなる。(5) 帰属表現が1文に0.5回というのはウィキニュース固有の高さで、新聞では「同社によると」を段落に1回程度に抑える。

### 3.4 press プロファイルの決定

上の実測から `GENRE_PROFILES["press"]` を次のように定めた（`skills/natural-japanese/scripts/lint.py`）。

- `disabled_categories`: `low_burstiness`, `nominal_ending`, `high_bullet_ratio`, `high_bold_density`, `boilerplate_heading`, `numbered_phase_structure`
- `severity_overrides`: `translationese` と `translationese_morph` を `info`（新設した仕組み。検出は残し、severity だけ下げる）
- `lead_repeat_threshold`: 7（business と同じ）
- `reading_load_sentence_max_chars`: 100

構造層の無効化は実測ではなく発表文の慣習（「■背景」のような定型見出し、仕様の箇条書き）から決めた。既存の fixture（`natural.md` 0件、`ai-smelly.md` 25件）は default のままなので影響しない。`ai-smelly.md` に `--genre press` を当てると `low_burstiness` の1件が消えて24件になり、`translationese` 5件は info になる。

## 4. 忠実性検査（factcheck.py）の設計根拠

PR TIMES の審査で最多の指摘が「最上級表現の根拠不足」であること、広報向けの手引きが揃って「事実と数字で書く」「主観と広告表現を避ける」と述べていること、そしてニュース文の実測で最上級・評価語が記事あたり中央値0であることから、機械照合の対象を次に絞った。

- 数値（単位・期間つき）と日付: ソースにない値は critical。値が一致して単位が違うものは info（換算の疑い）
- 固有名詞（sudachipy の固有名詞、法人格の有無と空白を吸収）、カタカナ語（3字以上）、英字略語・型番、URL・メール: ソースにないものは warn。「クラウド」「AI」のような言い換えによる情報の追加を拾う
- 「」内の引用（12字以上）: ソースと一字一句一致しなければ critical。近い文字列があれば「要約か改変」と添える
- 最上級・評価語: ソースにあれば info（根拠の記載は人が確認）、なければ warn
- 推定の語（見込み・予定・期待され）: 常に info。ソース側の有無を添える
- 網羅: ソースにある単位つき数値・日付・固有名詞のうち原稿に出てこないものを info で列挙

判断はしない。fixture（`skills/press-japanese/scripts/fixtures/`）で、忠実な原稿は unsupported 0件、意図的に9件の捏造を混ぜた原稿は9件を検出することを `dev/check-press-fixtures.sh` で固定している。

## 5. 未計測の範囲と、再校正の手順

この環境の外向き通信は検索エンジンの要約と GitHub の raw ファイルに限られ、prtimes.jp、各社のニュースルーム、新聞社サイト、文化庁サイト、Wayback Machine はいずれも遮断されていた。したがって次は未計測のままである。

- 大企業のプレスリリース本文（敬体の発表文）での lint の誤検知率。とくに `low_burstiness` と `low_sentence_variance` が敬体の発表文でどう振る舞うか
- 新聞社の記事本文そのもの（ウィキニュースは代替）
- 現行の大規模言語モデルが素で書いた発表文の検出率（このスキルの `ai-smell-in-press.md` は公開された指摘に基づく）

再校正の手順。取得できる環境で、2022年以前に公開された大企業のニュースリリースを `corpus/sources.json` に `genre: "press"` で追加し、`corpus/fetch.py` で取得する。候補となる公開アーカイブ（いずれも2010年代のリリースを年別に保持している）: トヨタ自動車 グローバルニュースルーム（global.toyota/jp/newsroom/）、ソニー プレスリリース アーカイブ（sony.jp/CorporateCruise/Press/archive.html）、パナソニック（news.panasonic.com/jp/press/）、日立製作所（hitachi.co.jp/New/cnews/month/）、NTT（group.ntt/jp/newsrelease/）、任天堂（nintendo.co.jp/corporate/release/）、JR東日本（jreast.co.jp/press/）。PR TIMES は企業ページ（prtimes.jp/main/html/searchrlp/company_id/…）から2022年以前の配信分を選ぶ。取得後、`corpus/experiments/press/analyze_wikinews.py` の `run_set` にファイル群を渡して同じ表を出し、人間側の文書発火率が5%を超える検出器を `press` プロファイルで無効化または閾値調整する。AI側は `corpus/generate.py` に発表文のトピック（新製品・提携・人事・研究成果）を足して現行モデルで生成すれば比較できる。

## 6. 限界

ウィキニュースは新聞ではなく、書き手はボランティアで、帰属句の多さや一文の長さは新聞より偏っている。GPT-2 日本語版（2020年）との比較は「生成モデルが再現しにくい型」の傍証にはなるが、現行モデルの癖の実測ではない。本文が1段落で収録されているため、段落構造の検出器は評価していない。fixture の原稿はこのスキルの作成者（AI）が書いたもので、人間コーパスではない。

これらの限界は、`press` プロファイルが「ニュース文で誤検知しない」ことを保証しても「発表文で誤検知しない」ことまでは保証しない、という形で残る。だから `press-japanese` の工程は、lint の findings を疑いの提示として扱い、忠実性は別の機械検査（factcheck.py）と人の判断で守る設計にしてある。
