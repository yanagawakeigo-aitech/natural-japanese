# モデル非依存の仕組みと、モデル別の推奨

このスキルは「どのモデルで動かしても、出てくる発表文の忠実さと読みやすさが一定以上になる」ことを狙って組んである。モデルの賢さに頼る部分を減らし、賢さがなくても守れる手順と機械検査に置き換える、という方針だ。それでも起草の自然さは最後にモデルの力量が出るので、段階ごとに推奨モデルを書いておく。

## モデルに頼らない5つの仕掛け

1. **中間表現を必ず作る**。原稿の前に事実表（`assets/fact-sheet-template.md`）を書かせる。モデルは「表にある事実だけを使う」という制約のほうが、「創作するな」という禁止より守りやすい。表は人が読めるので、弱いモデルの抽出ミスを人が直せる
2. **構造をテンプレートで固定する**。`assets/` の骨組み（リリース・記事・お知らせ・研究成果）に埋めていく。逆三角形や5W1Hをモデルが自力で組み立てる必要がない
3. **検査は機械が決定的に行う**。`scripts/factcheck.py` が原稿の数値・日付・固有名詞・引用・最上級をソースと突き合わせ、`natural-japanese/scripts/lint.py --genre press` がAI臭を検出する。モデルは自分の捏造にも自分の癖にも気づきにくいが、突きつけられた findings を仕分けることはできる
4. **収束を状態で終える**。「unsupported の finding がゼロか理由つきで残す、lint の新規 finding がゼロ、【要確認】が一覧化されている」の3条件がそろうまで回す。回数で終えない
5. **人に返す箇所を明示する**。埋められない事実は【要確認】で残し、納品時に一覧にする。モデルが埋めた空白は人が見つけにくいが、モデルが空けた空白は人が埋められる

## 段階ごとに求められる能力

| 段階 | 必要な力 | 弱いモデルでの代替 |
|---|---|---|
| 事実表の抽出 | 長い資料を落とさず読む正確さ | 資料を分割して2回に分ける。抽出後に `factcheck.py --source 資料 事実表` で表自体を照合する |
| 設計（核・骨組み・濃淡） | 判断力 | doctype の雛形をそのまま使い、濃淡は「リードとF1〜F3を厚く、他は一言」に固定する |
| 起草 | 日本語の自然さ、指示追従 | 骨組みの節ごとに分けて書かせ、節ごとに factcheck を回す |
| 検査 | 機械 | 変わらない |
| 判断台帳の仕分け | 推論力 | `unsupported_*` は原則すべて「直す」に倒し、「残す」の判断だけ人に返す |
| 最終通読 | 読み手としての感度 | 上位モデルに最終通読だけ委ねる |

## Claude での推奨

Claude Code で使うなら、起草と判断台帳の仕分けは `claude-opus-5` 以上を推奨する。effort は high を既定にし、対外発表で失敗コストが高いときは xhigh。`natural-japanese` の実測でも、effort を低く絞るとフル工程の検査を合理化で省きやすいことが確認されている。

- `claude-opus-5`（effort high〜xhigh）: 事実表 → 設計 → 起草 → 仕分けまで一貫して任せられる既定
- `claude-sonnet-5`: 事実表の抽出、短いお知らせ、factcheck 後の再突合には十分。長いリリースの起草は Opus に戻す
- `claude-haiku-4-5`: 起草には使わない。忠実性の確認に人手がかかりすぎる
- `claude-fable-5-1`: 上場企業の適時開示に近い発表、訂正リリースのような失敗コストが極端に高い最終稿の通読に。思考は常時オンで料金も Opus より高いので、全工程に使う必要はない

セッションのモデルと effort は `/model` と `/effort` で切り替える。この SKILL.md はフロントマターで `model` や `effort` を固定していない。組織の設定を上書きしないためだ。

## Codex での推奨

Codex CLI では、ChatGPT ログイン時の既定モデル（2026年9月時点で gpt-5.5 系）をそのまま使い、`~/.codex/config.toml` で推論の深さを上げる。

```toml
model_reasoning_effort = "high"
```

1回だけ上げるなら `codex -c model_reasoning_effort='"high"'`。軽量モデル（mini 系）は起草に使わない。バッチで回すなら `codex exec --skip-git-repo-check "<プロンプト>"` に、事実表と骨組みをファイルで渡す。

## それ以外のエージェント

Cursor・Windsurf・Aider など AGENTS.md を読むエージェントは、`npx openskills sync` で `<available_skills>` に登録すれば同じ SKILL.md を読む。`uv` が使えない環境では `references/checklist.md` の手動チェックで機械検査を代替する。忠実性の手動突合は面倒だが省略しない。ここを省くと、このスキルは「文章が上手なだけの捏造機」になる。

## 弱いモデルで回すときの分割手順

1回で全部をやらせず、3回に分ける。

1. 「次の資料から事実表を作れ。表にない情報を足すな」→ 事実表。`factcheck.py` で資料と照合
2. 「事実表と `assets/<doctype>` の骨組みを使い、各節に使う事実のIDだけを割り当てろ」→ 節ごとのID割り当て
3. 「割り当てたIDの事実だけを使い、節ごとに本文を書け」→ 原稿。`factcheck.py` と `lint.py --genre press`

分けるほど自然さは落ちやすいが、忠実さは保てる。最後の通読だけ上位モデルに回すと両立しやすい。

## サンプリングについて

決定的な出力を好む作業なので、temperature を選べる環境では低めにする。Claude の現行モデル（Opus 5、Sonnet 5、Fable 5.1）は temperature を受け付けないので、effort で制御する。
