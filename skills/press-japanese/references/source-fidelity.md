# ソース忠実の原則 — ソースにないことは書かない

広報文と報道文は、書き手の発想を披露する場ではない。ソース（発表資料・社内メモ・取材メモ・論文・既存のリリース）にある事実を、読み手が受け取りやすい順序と表現に組み替える仕事であり、組み替えの過程で情報が増えたり歪んだりしたら、それは誤報になる。生成AIは空白をもっともらしく埋める癖を持つ。数値の桁、発売日、担当者の肩書、業界の背景、顧客の声、経営者の意気込み。どれも「それらしい」ものを一瞬で作れてしまうから、忠実さをモデルの善意に任せず、手順と機械検査で守る。

原則は三つ。**追加しない。逸脱しない。創作しない。** 書けない箇所は推測で埋めず、【要確認】と明示して残す。

## 三つの禁止

**追加禁止**。ソースにない数値・固有名詞・日付・背景説明・業界動向・効果の推定を書き足さない。「市場は年々拡大している」「多くの企業が課題を抱えている」といった一般論の背景も、ソースが述べていなければ追加にあたる。もっともらしいほど危険で、記者はそこを裏取りしようとして矛盾を見つける。

**逸脱禁止**。ソースの主張の範囲を広げない、確度を上げない。「一部の店舗で試験導入」を「全国で展開」に、「2027年春の提供を予定」を「提供を開始」に、「目標」を「実績」に、「〜を目指す」を「〜を実現」に変えない。単位・期間・母数・比較対象を落とすのも逸脱で、「前年比20%増（4〜6月、既存店ベース）」の括弧を落とすと別の主張になる。

**創作禁止**。引用コメント・エピソード・顧客の声・利用者数・受賞歴を作らない。コメント枠が必要なら「代表者コメントは〇〇氏に依頼」と書いてユーザーに渡す。ソースに発言があっても、「」で囲む以上は一字一句そのままにする。要約するなら「」を外して伝聞にする。

## 許される操作

言い換え（意味を保ったまま表現を変える）、並べ替え（逆三角形にする）、圧縮（削る）、表記統一（`press-style.md` の規範に合わせる）、単位換算（元の数値を併記し、計算を備考に残す）。用語の説明は、ソース内に説明があればそれを使い、なければ一般に定着した定義に限り、【要確認】を付けて書く。独自の解釈や比喩による説明は書かない。

## 事実表（ファクトシート）— 原稿が引ける唯一の井戸

書く前に、ソースから事実を1行1件で抜き出して表にする。雛形は `assets/fact-sheet-template.md`。原稿に書いてよいのはこの表にある事実だけで、表にない数値や固有名詞が原稿に現れたら、それは追加か創作のどちらかだ。列は次のとおり。

| 列 | 書くこと |
|---|---|
| ID | F1, F2, …（原稿側の照合に使う） |
| 種別 | 誰が／何を／いつ／どこで／なぜ／どのように／いくら／数値／引用／固有名詞／背景／今後／評価 |
| 内容 | ソースの表現をなるべくそのまま。数値は単位・期間・母数つき |
| 出典 | ファイル名と行（またはページ）。複数ソースが食い違うなら両方書く |
| 確信度 | 明記（ソースが断定している）／推定（ソースが「見込み」「予定」と書いている）／要確認（ソースが曖昧、または食い違う） |
| 使用 | 使う／使わない（社外秘・未確定・根拠のない評価語は「使わない」） |
| 備考 | 換算の計算、表記統一の判断、食い違いの内容 |

「使わない」行を消さないこと。書かないと決めた根拠が残るし、ユーザーが「なぜこれが入っていないのか」と聞いたときに答えられる。

事実表を作る段階で、次の穴を必ず点検する。発表主体の正式名称、発表日と解禁日、価格（税込・税別）、提供開始日、対象（誰が使えるか）、問い合わせ先。プレスリリースはこの6点のどれかが欠けると配信できない。欠けていたら原稿を書く前にユーザーに聞くか、【要確認】の行を立てる。

## 確信度は語尾でなくラベルで

ソースが断定していることは断定で書く。ソースが「見込み」「予定」と書いていることは、その語を落とさずに書く。ソースが曖昧なことは、曖昧なまま書くのではなく【要確認: 発売日はソースに記載なし】のように角括弧で残す。「〜と思われます」「〜と言われています」のような語尾のぼかしで確信度を下げるのは、責任の所在を消す書き方であり、発表文では使わない。記事で推定を書けるのは「〜とみられる」「〜する方針だ」のように、ソース（取材）に推定の根拠があるときだけ。

## 数値・日付・固有名詞の扱い

数値は、単位・期間・母数・比較対象・「約」「以上」「未満」を落とさない。増減率（20%増）と増減幅（20ポイント増）を混同しない。換算するときは「約1万2000人（前年の1.2倍）」のように元の数値が復元できる形にし、計算を事実表の備考に残す。

日付は、発表日・発売日・提供開始日・解禁日を区別する。「本日」はリリースの発信日を指し、発信日が事実表にないなら「本日」と書かない。記事では「〇日」で書き、月をまたぐなら月も書く。

固有名詞は、正式名称をソースで確認する。ソース内で表記が揺れていたら、事実表で正式表記を1つ決め、原稿全体をそれに合わせる。ソースだけでは正式名称が確定できないとき（登記上の社名、製品の正式表記）は【要確認】にする。

## factcheck.py の findings の読み方

`scripts/factcheck.py` は原稿から数値・日付・固有名詞・カタカナ語・英字略語・「」内の引用・最上級表現を機械的に抜き出し、ソース（と事実表）に同じものがあるかを照合する。判断はしない。出てきた findings を次の方針で仕分ける。

| カテゴリ | 意味 | 対応 |
|---|---|---|
| `unsupported_number` | 原稿の数値がソースにない | 事実表に戻って確認。換算・丸めなら備考に計算を書き、なければ削るか【要確認】にする |
| `unsupported_date` | 原稿の日付がソースにない | 同上。「本日」を具体日に展開した場合は発信日の行を事実表に足す |
| `unsupported_proper_noun` | 固有名詞・カタカナ語・英字略語がソースにない | 表記ゆれ（「株式会社」の有無、全角半角）なら事実表の正式表記に合わせる。ソースにない語なら追加にあたるので削る |
| `unsupported_quote` | 「」内の文字列がソースと一致しない | 引用は一字一句一致させる。要約なら「」を外して伝聞にする |
| `superlative_without_source` | 「初」「最大」「No.1」などの根拠語がソースにない | 削る。ソースに根拠があるなら根拠（調査名・時期・対象）を同じ文か注記に書く |
| `superlative_in_source` | 根拠語はソースにある | 根拠の記載があるか確認する（機械は根拠の有無を判定しない） |
| `speculation_marker` | 「見込み」「期待される」「可能性」など推定の語 | ソースに同じ推定があるか確認。なければ逸脱 |
| `source_fact_unused` | ソースにある数値・固有名詞が原稿に出てこない | 情報。意図して落としたか点検する（5W1Hの欠落の疑い） |

すべてを機械的に潰す必要はないが、`unsupported_*` を「残す」にするときは、理由（表記ゆれ・換算・ユーザー指示）を台帳に書く。理由なしの「残す」は忠実性の放棄になる。

## 判断台帳

`natural-japanese` の判断台帳と同じ形式で、finding ごとに1行書く。動詞は四つ。

```
- [直した] unsupported_number「約3万人」: 事実表F7の「2万8400人」に戻した
- [ソースへ戻した] unsupported_quote: 要約になっていたので「」を外し「〜と述べている」にした
- [要確認に変更] unsupported_date「10月1日提供開始」: ソースに開始日なし。【要確認】に置き換えた
- [残す/表記統一] unsupported_proper_noun「ソラベース」: 事実表F1で「ソラベース株式会社」の略称と決めた
```

## 納品時 — 【要確認】をゼロにするために推測で埋めない

原稿とあわせて、【要確認】の一覧と、事実表の「使わない」行のうちユーザーが判断すべきもの（評価語・未確定情報）を渡す。空欄が残ることは失敗ではない。空欄を推測で埋めて配信されることが失敗だ。

## 背景 — なぜ「抜き出してから書く」のか

原稿を書いてから事実を照合するより、先に事実を単位ごとに抜き出し、そこから書くほうが捏造は減る。要約研究では、原文から主張を単位ごとに抽出し、支持関係を確かめたうえで書き直す「抽出 → 選択 → 書き直し」の型が、文単位の出典追跡を保ったまま忠実性を上げると報告されている（例: "Faithful by Construction: Claim-Anchored Attribution for Multi-Document Summarization", arXiv:2606.23989）。原文から根拠となる箇所を先に引用させ、その引用だけから答えを組み立てる「quote-then-answer」の作法も同じ発想にある。このスキルの事実表は、その型を人が読める表にしたものだ。
