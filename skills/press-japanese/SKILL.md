# press-japanese

発表文と報道文を、ソースに忠実に、記者が当たり前に読める日本語で書くためのスキル。プレスリリース（PR TIMES型）、新聞記事（発表もの）、HP掲載のお知らせ、研究成果リリースを扱う。`natural-japanese` の設計（検出は機械、判断はAI。事後修正より生成時制約）をそのまま受け継ぎ、そこに「ソース忠実」という広報固有の制約を足している。

## 設計思想

軸は三つ。第一に **ソースにないことは書かない**。追加しない、逸脱しない、創作しない。書けない箇所は推測で埋めず【要確認】として残す（`references/source-fidelity.md`）。第二に **生成AI登場前の作法を制約にする**。逆三角形、5W1Hのリード、記者ハンドブック準拠の表記、地の文は事実で評価はコメント枠、という新聞社と大企業の広報が守ってきた型に沿って書く（`references/press-style.md`）。第三に **忠実さをモデルの善意に頼らない**。原稿の前に事実表を作らせ、`scripts/factcheck.py` が数値・日付・固有名詞・引用・最上級をソースと突き合わせ、AI臭は `natural-japanese` の `lint.py --genre press` が検出する。モデルが変わっても手順と機械検査は変わらない（`references/model-workflow.md`）。

工程は「受け取り → 事実表 → 設計 → 執筆 → 検査 → 収束 → 納品」の順に進む。

## 実行モード

**クイック（既定）**: HPのお知らせ、短いリリース、既存文の手直し。サブエージェントを使わず、この場で完結させる。追加で読むのは該当する doctype 1ファイルだけでよい。事実表は簡略でよいが省略しない。検査は `press_check.py` を1回（`--source` を必ず渡す）。収束は新規 finding が出なければ1周で切り上げる。

**フル**: 対外配信するリリース、記事、研究成果リリース、ユーザーが「しっかり」「配信する」「訂正が許されない」と言ったとき。事実表を正式に作り、§5の検査に加えて§6の四つのレビュー（忠実性・文体・構造・記者視点）を行う。並列のサブエージェントに委ねてよいが、判断台帳への統合と「直す/残す」の判断は必ず親が行う。effort を選べる環境では high 以上を推奨する（低い effort は検査を合理化で省きやすい）。

どちらか迷ったら、まずクイックで仕上げてから「フルで磨き直せる」とユーザーに一言添える。

## 呼び出し方

- `/press-japanese [release|article|notice|research] [quick|full] <ソース>` — 書く（既定）。文書タイプを省略したら依頼から判断する
- `/press-japanese check <原稿> --source <ソース>` — **検査のみ**。書き換えず、忠実性・文体・AI臭の所見と【要確認】一覧を返す
- `/press-japanese factsheet <ソース>` — 事実表だけを作る（配信前の確認や、別のモデルで起草するときの中間成果物）

自然言語でも同じ。「このメモからPR TIMES用のリリースを書いて」→ release、「リリースを新聞記事風に」→ article、「この発表文に捏造がないか見て」→ check。

## 1. 受け取り — ソースを確定させる

ユーザーから渡された資料をすべて列挙し、一次（発表主体が書いたもの、論文、取材メモ）か二次（他社の記事、要約）かを分ける。ソースがない依頼（「〇〇のリリースを書いて」だけ）には、書く前に素材の提供を求める。`natural-japanese` の「素材集め（Web検索で足す）」はこのスキルでは使わない。検索で足した情報は追加にあたる。ユーザーが明示的に「公開情報で補ってよい」と言った場合だけ、出典URLつきで事実表に入れ、確信度を「要確認」にする。

発表主体の正式名称、発信日、解禁日、提供開始日、価格、対象、問い合わせ先の7点は、この段階で有無を確かめる。欠けていたらユーザーに聞くか、【要確認】の行を立てて先へ進む。

## 2. 事実表 — 原稿が引ける唯一の井戸

`assets/fact-sheet-template.md` に沿って、ソースから事実を1行1件で抜き出す。内容はソースの表現のまま、数値は単位・期間・母数つき、出典はファイル名と行、確信度は明記／推定／要確認。使わないと決めた行（社外秘・未確定・根拠のない評価語）も「使わない」として残す。原稿に書いてよいのはこの表にある事実だけで、表にない数値や固有名詞が原稿に出たら追加か創作のどちらかになる。

表を作ったら、表自体をソースと照合する: `uv run scripts/factcheck.py <事実表> --source <ソース>`。抽出の段階で数値を写し間違えると、以降の工程すべてが間違った事実を守ることになる。

## 3. 設計 — 型と核と濃淡を決める

文書タイプを確定し、対応する型を読む。

- プレスリリース → `references/doctypes/press-release.md`
- 報道記事（発表もの） → `references/doctypes/news-article.md`
- HP掲載のお知らせ → `references/doctypes/web-notice.md`
- 研究成果リリース → `references/doctypes/research-release.md`

次にニュースの核を一文で書く（「誰が、いつから、何を、いくらで、誰に向けて」）。書けないなら事実表に穴がある。骨組みは `assets/` の該当スケルトンをコピーし、各節に使う事実表のIDを割り当てる。IDを割り当てられない節（背景・コメント・今後）は削る。濃淡は、リードと「何が新しいか」を厚く、定型部（会社概要・問い合わせ先）は型どおりに。

文体は文書タイプで決まる。リリースとお知らせは「です・ます」、記事は「である・した」。混ぜない。

## 4. 執筆 — 型の中で、事実表だけを使って書く

`references/press-style.md` を制約として書く。要点だけ挙げると——リードは発表主体を主語に5W1H（発表文は5W2H）を1〜3文で、逆三角形で重要な順に、一文は40〜60字前後で一文一義、数字は算用数字で単位・期間つき、日付は西暦、初出は正式名称で略称は「以下、〇〇」、自社役員に敬称なし、一人称は「当社」（記事は「同社」）、地の文に評価語を置かず評価はコメント枠へ、最上級と「初」は根拠を同じ文か注記に、敬語は一段。`natural-japanese` の文体憲法12条も土台として効くが、第2条（見出しはメッセージ）は発表文の本文見出しでは緩めてラベルでよい。

書きながら、事実表のIDを段落末に（F1, F4）のように仮置きしておくと、検査が速い。納品時に外す。

## 5. 検査(1) — 機械検査

```
uv run scripts/press_check.py <原稿> --source <ソース1> [--source <ソース2>...]
```

`press_check.py` は三つを一度に回す。`factcheck.py`（忠実性: 原稿にあってソースにない数値・日付・固有名詞・カタカナ語・引用・最上級を列挙）、広報常套句の密度（「実現」「貢献」「につきまして」の重なり）、`natural-japanese` の `lint.py --genre press`（AI臭。同スキルの `scripts/lint.py` を自動で探し、見つからなければ省略を告げる）。検出結果は疑いの提示で、件数に関わらず exit code 0。各ツールを個別に回してもよい。

`uv` が使えない環境では `references/checklist.md` で同じ観点を人手でなぞる。忠実性の突合は省略しない。

findings のカテゴリごとの読み方は `references/source-fidelity.md` の表と、`natural-japanese/references/revision-guide.md` の対応表を使う。

## 6. 検査(2) — 判断台帳と四つのレビュー

findings は一つひとつ「直した／ソースへ戻した／要確認に変更／残す（理由）」で台帳に記録する。`unsupported_*` を「残す」にできるのは、表記ゆれ・換算（計算を備考に残す）・ユーザーの明示的な指示のどれかがあるときだけ。理由なしの「残す」は忠実性の放棄になる。

**忠実性レビュー**。factcheck が拾えない追加を目視で探す。ソースにない背景説明（「昨今〜が求められる中」）、効果の因果（「〜により〜が向上」）、対象の拡大（「一部店舗」→「全国」）、確度の格上げ（「予定」→「開始」）、コメントの捏造。段落ごとに「この段落はソースのどの行から来たか」を指させるかを確かめる。

**文体レビュー**。`references/press-style.md` の表記（数字・日付・固有名詞・敬称・敬体常体）と `references/ai-smell-in-press.md` のカタログを当てる。抽象動詞が1文に2つ以上ないか、装飾語が地の文にないか、冒頭と結びがテンプレになっていないか。

**構造レビュー**。リードだけを切り出して読み、記者が短い記事を書けるかを確かめる。次に見出しと各段落の先頭文だけを読み（`natural-japanese/scripts/outline.py` で抽出できる）、逆三角形になっているか、後ろの段落から削っても成立するかを見る。doctype の「必須要素」と「AIがやりがちな失敗」も照合する。

**記者視点レビュー**（フルのみ）。初見の記者として、これは何のニュースか・いつからいくらで誰向けか・何が今までと違うか（数値で）・この主張は誰のものか・裏取りの電話をどこにかけるか、の5問に原稿だけで答えられるかを確かめる。答えられない問いはソースの穴であり、【要確認】に起こす。

## 7. 収束

台帳の「直した」を反映したら `press_check.py` を再実行する。出口は三つの状態がそろったとき。(1) `unsupported_*` がゼロか、理由つきで「残す」になっている、(2) lint の新規 finding がない、(3) 【要確認】が原稿中と一覧の両方にあり、推測で埋められていない。同じ finding が2周続けて再発したら、`natural-japanese/references/revision-guide.md` の「発散ガード」に従う。

既存の発表文を直すときは、直す箇所を選ぶ。全見出しを同じ型に揃える、全箇条書きを地の文に均す、といった一律の改稿は元の文書の濃淡を消して逆にAI臭を増やす（同「改稿を一律に適用しない」）。忠実性に関わる修正だけは一律に行う。

## 8. 最終パス — 声に出して読む

検査が収束しても、既知のパターンが消えたことしか意味しない。最後に初見の読者（記者、顧客、記者会見の質問者）として通読し、声に出して読むつもりでリズムを確かめる。「発表文として当たり前に読めるか」「盛っている印象がないか」「どこかに温度のない整いすぎがないか」。違和感があれば台帳に起こして§7へ戻る。

## 9. 納品と後片付け

原稿とあわせて、【要確認】の一覧（何が・なぜ不明か・誰に確認するか）と、事実表の「使わない」行のうちユーザーが判断すべきもの（評価語・未確定情報・コメント依頼）を渡す。空欄が残ることは失敗ではない。空欄を推測で埋めて配信されることが失敗だ。

作業中に作った事実表・台帳・factcheck のJSON・下書きは、ユーザーが明示的に望まない限りプロジェクトに残さない。原稿中の（F1）のようなID仮置きも外す。
